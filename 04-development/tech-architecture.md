## RAG 实现策略（Demo 阶段：轻量级）

### 为什么 Demo 阶段不做向量检索？

1. **时间成本**：向量数据库搭建 + Embedding 模型选择 + 检索调优，至少需要 2-3 天
2. **数据量**：种子数据只有 5-10 个岗位，向量检索的优势体现不出来
3. **可替代**：关键词匹配 + 岗位类别映射在数据量小时效果相当

### Demo 阶段实现

```
用户输入 JD
    ↓
提取关键词（岗位名称、技术栈、行业等）
    ↓
岗位类别映射（前端/后端/产品/运营/设计...）
    ↓
从种子知识库中匹配对应岗位的经验数据
    ↓
将经验片段注入 Prompt 上下文
    ↓
调用大模型生成解读报告
```

## 用户贡献机制（设计，Demo 不实现）

```
用户使用解读
    ↓
报告底部出现"这个解读准确吗？你有补充吗？"
    ↓
用户提交自己的真实经验
    ↓
后台人工审核
    ↓
审核通过 → 入库 → 下次同岗位解读时注入
    ↓
形成"经验飞轮"：使用越多 → 经验越多 → 解读越准 → 用户越多
```

## 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 小程序框架 | 微信原生 / UniApp | 快速开发，SOLO 支持好 |
| 后端 | Node.js + Express | 轻量，SOLO 擅长 |
| 数据库 | SQLite / JSON 文件 | Demo 阶段够用，无需部署 |
| AI 模型 | 豆包 API / DeepSeek | 成本低，中文能力强 |
| 部署 | 微信云开发 / 腾讯云 | 小程序生态集成好 |

## SOLO 辅助开发策略

| 开发环节 | SOLO 能力 | 预期效果 |
|---------|----------|---------|
| 需求拆解 | 任务分解 + 计划生成 | 结构化开发计划 |
| 前端开发 | 代码生成 + 组件设计 | 小程序页面快速搭建 |
| 后端开发 | API 设计 + 逻辑实现 | 接口快速开发 |
| Prompt 设计 | 迭代优化 + 测试 | 高质量解读 Prompt |
| 测试 | 测试用例生成 | 质量保障 |
| 文档 | 自动生成 | 开发记录 + 实践帖素材 |
