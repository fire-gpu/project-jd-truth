# 路线 B 功能优化规划

> 日期：2026-04-18
> 产品：JD 说真话（微信小程序）
> 版本：V0.1 Demo 阶段
> 背景：当前已完成玫红色改版，用户反馈"标准化、没审美"，需要在有限时间内做最高价值的功能优化

## 一、报告导出格式决策

### 1.1 方案对比

| 方案 | 优点 | 缺点 | 实现复杂度 | 用户体验 | 微信小程序适配性 |
|------|------|------|-----------|---------|----------------|
| A. 导出为 HTML 文件 | 简单、样式一致、手机可直接打开 | 不是"文档"感觉，编辑不方便，微信内无法直接预览 | **低**（1-2h） | 中 | 中（需用 `wx.openDocument` 或保存到本地） |
| B. 导出为 DOC/DOCX | 正式文档感、可编辑、可打印、求职场景刚需 | 实现复杂（需引入 docx 库或后端生成），样式可能走样 | **高**（需后端配合，3-5h） | 高 | 高（`wx.openDocument` 原生支持 .docx） |
| C. 导出为 PDF | 不可编辑、格式最稳定、适合打印 | 小程序端生成 PDF 极难（需 canvas 绘制或后端），文件体积大 | **很高**（需后端，5-8h） | 高 | 中（`wx.openDocument` 支持 PDF，但生成困难） |
| D. 生成分享海报（图片） | 传播性强、适合社交媒体、Demo 演示效果好 | 信息量有限、不可编辑、长报告截断 | **中**（canvas 绘制，2-3h） | 高（社交场景） | 高（`canvas` API 成熟，可直接保存到相册） |
| E. 复制到剪贴板（纯文本/Markdown） | 最简单、通用、零依赖 | 没有格式、体验一般、用户感知低 | **最低**（0.5h） | 低 | 高（`wx.setClipboardData` 原生支持） |

### 1.2 推荐方案：D + E 组合，B 作为后续迭代

**第一优先：D. 生成分享海报（图片） + E. 复制到剪贴板**

**理由：**

1. **Demo/参赛场景的特殊需求**：当前是 V0.1 Demo 阶段，核心目标是展示产品价值。分享海报在演示时视觉冲击力最强，评委/观众能直观感受到"这是一个有用的工具"。这是**投入产出比最高**的选择。

2. **微信生态天然适配**：小程序的 `canvas` 2D API 已经很成熟，生成图片后可以直接 `wx.saveImageToPhotosAlbum` 保存到相册，或通过 `wx.shareFileMessage` 发送给好友。整个链路在微信生态内闭环，无需跳出。

3. **传播性**：求职者看到有价值的 JD 解读，大概率会分享给同样在找工作的朋友。图片形式在微信群传播效率远高于文档。

4. **实现成本可控**：canvas 绘制海报是小程序常见能力，预计 2-3 小时可完成。核心工作是设计海报模板（品牌 Logo + 报告摘要 + 二维码），可以复用现有的玫红色设计系统。

5. **复制到剪贴板作为兜底**：对于需要编辑报告内容的用户（比如想复制到 Word 里自己排版），提供"复制全文"按钮，成本极低（0.5h），但覆盖了"导出"的基础需求。

**第二优先（后续迭代）：B. 导出为 DOCX**

- 求职者确实有"保存为正式文档"的需求，但这需要后端配合（前端生成 docx 文件不现实），实现成本高。
- 建议在 V0.2 或有后端支持后再做。可以用 `docx` npm 包在 Node.js 端生成，小程序端通过 API 下载后用 `wx.openDocument` 打开。
- **不推荐在 Demo 阶段投入**：3-5 小时的开发时间用在 UI 优化上价值更高。

**明确不推荐：C. PDF**

- 小程序端没有原生 PDF 生成能力，canvas 逐页绘制太复杂且效果差。
- 后端生成 PDF（如 puppeteer）成本更高，且 PDF 在手机上阅读体验不如图片。
- 除非有明确的"打印"需求，否则不值得投入。

### P0（必须做，影响核心体验）

#### 2.1 输入区域优化 -- 粘贴按钮 + 输入体验提升

**当前问题**：用户的核心操作是"粘贴 JD 文本"，但当前只有一个普通 textarea，没有粘贴快捷入口。用户从招聘 App 复制 JD 后，需要长按粘贴，体验不够流畅。

**优化方案**：
- 在 JD 输入框右上角增加"粘贴"按钮（调用 `wx.getClipboardData`），用户一键粘贴
- 输入框高度从 `min-height: 280rpx` 增加到 `min-height: 360rpx`，给 JD 长文本更多空间
- 已有字数统计（`jdTextLength`），保持即可
- 增加输入框 focus 状态的视觉反馈（当前已有 `border-color: #FF2D55`，可增加轻微阴影）

**实现成本**：约 1 小时
**用户价值**：极高 -- 这是用户使用产品的第一步，粘贴体验直接影响首关转化率

#### 2.2 报告页底部操作栏 -- 固定悬浮

**当前问题**：报告页底部的"继续解读"按钮在页面最底部，用户看完长报告后需要滚动到底部才能操作。没有导出/分享入口。

**优化方案**：
- 在报告页底部增加固定悬浮操作栏（`position: fixed; bottom: 0`）
- 操作项：`保存图片` | `复制全文` | `继续解读`
- 半透明毛玻璃背景，不遮挡报告内容
- 报告页底部增加 `padding-bottom: 120rpx` 避免内容被遮挡

```css
.report-bottom-bar {
  position: fixed;
  bottom: 0;
  left: 0;
  right: 0;
  display: flex;
  align-items: center;
  justify-content: space-around;
  padding: 16rpx 32rpx;
  padding-bottom: calc(16rpx + env(safe-area-inset-bottom));
  background: rgba(255, 255, 255, 0.92);
  backdrop-filter: blur(20px);
  box-shadow: 0 -4rpx 24rpx rgba(0, 0, 0, 0.06);
  z-index: 100;
}
```

**实现成本**：约 1.5 小时
**用户价值**：极高 -- 随时可操作，且为导出功能提供入口

#### 2.3 骨架屏加载 -- 替代转圈 loading

**当前问题**：报告生成时只有一个旋转圆圈 + "报告生成中，请稍候..."文字。AI 生成通常需要 2-5 秒，用户等待时没有预期感。

**优化方案**：
- 用骨架屏（Skeleton Screen）替代转圈 loading
- 骨架屏结构模拟报告页布局：标题区 + 3 个核心维度卡片 + 扩展维度卡片
- 使用渐变动画（shimmer effect）让骨架屏有"加载中"的感觉
- 保留底部的"报告生成中..."提示文字

```css
.skeleton-block {
  background: linear-gradient(90deg, #F0F0F0 25%, #E8E8E8 50%, #F0F0F0 75%);
  background-size: 200% 100%;
  animation: shimmer 1.5s infinite;
  border-radius: 12rpx;
}

@keyframes shimmer {
  0% { background-position: 200% 0; }
  100% { background-position: -200% 0; }
}
```

**实现成本**：约 2 小时
**用户价值**：高 -- 让用户预知报告结构，减少等待焦虑，提升专业感

### P1（应该做，提升品质感）

#### 2.4 维度卡片设计感提升

**当前问题**：报告页的维度卡片通过 `rich-text` 渲染 HTML，虽然已有 `border-left` 颜色区分和卡片阴影，但整体视觉层次感不够强。核心维度和扩展维度的区分仅靠标签文字颜色不同（`#FF2D55` vs `#FF8FA3`），感知度弱。

**优化方案**：
- 为每个维度增加图标（使用 emoji 或 iconfont）：工作内容用工具图标、能力要求用靶心图标、行动建议用路线图标等
- 核心维度卡片使用更深的背景色或更粗的左边框（`8rpx`），扩展维度用更浅的样式
- 个性化维度（差距分析）使用特殊背景色（如浅蓝 `#F0F4FF`），突出"这是为你量身定制的"
- 维度卡片增加 hover/active 微交互

**实现成本**：约 2 小时（主要是调整 HTML 模板和 CSS）
**用户价值**：高 -- 报告页是产品的核心价值交付点，视觉品质直接影响用户对"AI 解读质量"的感知

#### 2.5 全局微动效

**当前问题**：页面切换、按钮点击、卡片出现都是瞬间变化，没有过渡动画，感觉"生硬"。

**优化方案**：
- 页面切换：利用小程序的 `wx.navigateTo` 默认动画即可，无需额外处理
- 按钮点击：已有 `transform: scale(0.98)` 和 `opacity: 0.9`，保持即可
- 卡片出现：使用 CSS `animation` + `@keyframes`，卡片从下方淡入滑出
- 报告维度卡片依次出现（stagger animation），每个延迟 100ms

```css
@keyframes slideUp {
  from {
    opacity: 0;
    transform: translateY(30rpx);
  }
  to {
    opacity: 1;
    transform: translateY(0);
  }
}

.report-section {
  animation: slideUp 0.4s ease-out both;
}

.report-section:nth-child(1) { animation-delay: 0.1s; }
.report-section:nth-child(2) { animation-delay: 0.2s; }
.report-section:nth-child(3) { animation-delay: 0.3s; }
```

**实现成本**：约 1.5 小时
**用户价值**：中高 -- 微动效是"高级感"的重要来源，但不是核心功能

#### 2.6 空状态优化

**当前问题**：历史页空状态只有一个 emoji + 文字 + 按钮，视觉上比较单薄。报告页的错误状态也只有一个 "!" 符号。

**优化方案**：
- 用 SVG 内联图标替代 emoji（更可控、更精致）
- 增加引导文案的层次：主文案 + 副文案
- 历史页空状态增加一个简单的插画（可以用 CSS 绘制或内联 SVG）
- 错误状态增加具体的错误描述和操作建议

**实现成本**：约 1 小时
**用户价值**：中 -- 空状态出现频率不高，但优化后能提升产品完成度

### P2（可以做，锦上添花）

#### 2.7 首页 Hero 区域插画/动效

**理由降级**：当前首页 Header 已有玫红渐变背景 + Logo + slogan，视觉效果已经不错。更精致的插画/动效（如 Lottie 动画）需要设计资源投入，且对核心转化率影响有限。在 Demo 阶段不值得优先投入。

**如果要做**：可以用 CSS 动画做一个简单的"放大镜扫描 JD 文本"的动效，纯代码实现，无需额外设计资源。约 2 小时。

#### 2.8 岗位选择图标化

**理由降级**：当前标签式选择已经清晰可用，增加图标需要设计 6 个岗位的图标资源。在 Demo 阶段优先级不高。

**如果要做**：使用 emoji 作为图标（前端/后端用代码符号、产品用灯泡、运营用喇叭、设计用画笔、数据分析用图表），无需设计资源。约 1 小时。

#### 2.9 全局字体优化

**理由降级**：当前已使用 `-apple-system, BlinkMacSystemFont, 'PingFang SC', 'Microsoft YaHei'`，在 iOS 上会自动使用苹方，在 Android 上使用微软雅黑，已经是最佳实践。引入思源黑体需要加载 webfont（约 2-4MB），会显著影响首屏加载速度。**不推荐在小程序中做**。

#### 2.10 历史页卡片式布局

**理由降级**：当前历史页已经是卡片式布局（`.history-card.card`），有圆角、阴影、分类标签、摘要、评分。已经满足需求，无需额外优化。

## 三、功能优先级

### 评估矩阵

| # | 功能 | 用户价值 | 实现成本 | 技术风险 | 综合评分 |
|---|------|---------|---------|---------|---------|
| 1 | 历史记录持久化（localStorage） | 高 | 低 | 低 | **极高** |
| 2 | 分享给朋友（小程序转发） | 高 | 低 | 低 | **极高** |
| 3 | JD 粘贴识别（自动提取 JD 文本） | 中 | 中 | 中 | 中 |

| 7 | 多语言（英文 JD 支持） | 中 | 高 | 中 | 低 |

### P0（核心功能）

#### 3.1 历史记录持久化（localStorage）

**当前状态**：从 `history.wxml` 可以看到历史页已有完整的 UI（列表、空状态、加载更多），但数据来源不明。如果当前是每次从服务端拉取，那么离线场景下历史会丢失。

**优化方案**：
- 每次生成报告后，将报告数据存入 `wx.setStorageSync`
- 历史页优先从本地读取，同时异步从服务端同步
- 设置本地缓存上限（如最近 50 条），超出后删除最旧的

**实现成本**：约 1.5 小时
**用户价值**：极高 -- 用户回看历史报告是高频需求，且离线可用是小程序的基本体验要求

#### 3.2 分享给朋友（小程序转发）

**当前状态**：当前没有任何分享能力。

**优化方案**：
- 实现 `onShareAppMessage`，支持转发到聊天
- 分享卡片标题：`[岗位名称] JD 解读报告 | JD说真话`
- 分享卡片路径：`/pages/report/report?id=xxx`（直接打开报告详情）
- 报告页底部操作栏增加"分享"按钮

```javascript
onShareAppMessage() {
  return {
    title: `${this.data.report.jobTitle || 'JD'} 解读报告 | JD说真话`,
    path: `/pages/report/report?id=${this.data.reportId}`,
    imageUrl: this.data.shareImageUrl || '/assets/share-cover.png'
  }
}
```

**实现成本**：约 1 小时
**用户价值**：极高 -- 分享是小程序增长的核心渠道，且实现成本极低。Demo 演示时也能展示"社交传播"能力

### P1（增强功能）

#### 3.3 JD 粘贴识别（自动提取 JD 文本）

**场景**：用户从招聘 App 复制内容时，可能复制了整个页面（包含公司介绍、福利待遇等非 JD 内容），需要自动识别并提取核心 JD 部分。

**方案**：
- 在用户粘贴内容后，用正则匹配常见的 JD 结构标记（如"岗位职责"、"任职要求"、"工作内容"等）
- 如果检测到 JD 结构，自动提取对应段落
- 如果无法识别，提示用户手动确认

**实现成本**：约 3 小时（主要是正则规则和边界情况处理）
**用户价值**：中 -- 能减少用户手动删除无关内容的操作，但不是刚需

#### 3.4 收藏/标记重要报告

**场景**：用户可能解读了多个 JD，想标记几个最感兴趣的岗位方便后续查看。

**方案**：
- 历史页每张卡片增加"收藏"星标按钮
- 收藏状态存入 localStorage
- 历史页顶部增加"收藏筛选"Tab

**实现成本**：约 2 小时
**用户价值**：中 -- 求职者确实有"对比多个岗位"的需求，但 V0.1 阶段优先级不高

### P2（未来迭代）

#### 3.5 报告对比（两份报告 diff）

**理由降级**：用户价值高（求职者经常在多个岗位间纠结），但实现复杂度高。需要设计对比视图（并排或上下）、高亮差异、维度对齐等。建议 V0.2 或后续版本再做。

#### 3.6 深色模式

**理由降级**：小程序的深色模式需要重新设计整套颜色系统（背景、文字、卡片、边框等），工作量大。且求职场景下用户使用时间短，深色模式不是刚需。

#### 3.7 多语言（英文 JD 支持）

**理由降级**：虽然产品名是"JD说真话"，但国内求职者主要看中文 JD。英文 JD 支持需要 AI 模型的多语言能力配合，且用户需求不明确。如果后续有海外求职场景再考虑。

## 四、推荐执行顺序

基于"用户价值 x 实现成本"矩阵，并考虑 Demo/参赛场景的特殊需求（视觉效果 > 功能完整性），推荐以下执行顺序：

## 五、总结

### 核心策略

1. **导出方案**：分享海报（图片）+ 复制到剪贴板，覆盖"传播"和"保存"两个核心场景，总投入约 2.5h
2. **UI 优化**：聚焦"输入体验"和"报告展示"两个用户感知最强的环节，骨架屏 + 悬浮操作栏 + 维度卡片提升是最高优先级
3. **功能补充**：localStorage 持久化 + 小程序转发是投入最低、价值最高的两个功能

### 总工时估算

| 批次 | 工时 | 交付重点 |
|------|------|---------|
| 第一批 | 6h | 核心体验闭环 |
| 第二批 | 4.5h | 视觉品质 |
| 第三批 | 3h | 锦上添花 |
| **合计** | **13.5h** | 完整的 Demo 级优化 |

### 风险提示

1. **canvas 海报生成**在不同机型上可能有渲染差异，需要真机测试
2. **骨架屏**需要和报告页的实际布局保持同步，后续报告结构变化时需要同步更新骨架屏
3. **localStorage** 有 10MB 上限，单条报告数据需控制体积（建议不存原始 JD 文本，只存摘要）
4. **分享功能**需要小程序已发布或处于体验版，开发版无法测试转发效果
