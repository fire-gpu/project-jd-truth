## 一、Prompt 设计质量评估（5 维度量表）

### 评分总览

| 维度 | 评分 | 简要理由 |
|------|------|---------|
| 真实性 | **4/5** | 幻觉边界规则覆盖全面（5 条硬规则），但缺少对"时间占比"编造的约束 |
| 完整性 | **5/5** | 3 核心 + 4 扩展 + 1 个性化维度，与 feature-spec 完全对齐，跳过规则清晰 |
| 具体性 | **4/5** | 每个维度都有格式示例和内容要求，但"JD 潜台词"的差距程度缺乏量化标准 |
| 可执行性 | **4/5** | 行动建议维度要求"预计时间+推荐资源"，可执行度高；但时间占比的"百分比估算"缺乏指导 |
| 差异性 | **4/5** | 知识库注入 + 幻觉边界 + 结构化输出显著超越通用 AI，但种子数据仅 6 条经验，差异化天花板受限 |
| **总分** | **21/25** | 达到"通过标准"（>=20），接近"优秀标准"（>=22） |

### 逐维度详细评估

#### 1. 真实性（4/5）

**优势**：
- 幻觉边界规则设计完善，5 条硬规则覆盖了编造来源、编造数字、不确定性标注、JD 原文优先、知识库诚实标注
- 每条规则都有明确的"禁止/允许"示例，AI 可执行性强
- 报告末尾强制包含数据来源说明
- 质量自检清单 12 项覆盖了主要幻觉风险点

**不足**：
- **时间占比缺乏约束**：Prompt 要求"每条必须包含时间占比（百分比估算）"，但没有约束 AI 不能凭空编造时间占比。例如 AI 可能写出"[60%] 架构设计"这种与实际严重不符的时间分配。建议增加"时间占比应参考知识库中的数据，如知识库无相关数据则使用'因团队而异'等模糊表述"
- **"差距程度"量化标准缺失**：JD 潜台词维度要求标注"差距程度"（高/中/低），但没有定义什么算"高"、什么算"中"，AI 可能主观判断不一致
- **缺少对"行业经验"类 JD 描述的幻觉约束**：如 jd_009 要求"有饮水机、净水机行业经验"，AI 可能编造该行业的具体工作内容

#### 2. 完整性（5/5）

**优势**：
- 核心维度（真实工作内容、核心能力要求、行动建议）100% 覆盖，与 feature-spec.md 完全一致
- 扩展维度（JD 潜台词、KPI/考核指标、团队协作模式、工作强度信号）全部覆盖，且每个维度都有明确的"出现条件"和"跳过条件"
- 个性化维度（差距分析）的出现/跳过条件清晰
- 质量自检清单确保 AI 输出前自检，降低遗漏风险

**无明显不足**。

#### 3. 具体性（4/5）

**优势**：
- 每个维度都有详细的格式要求和示例输出，AI 有明确的模仿模板
- "真实工作内容"要求包含"做什么、用什么工具、产出什么"
- "行动建议"要求包含"预计所需时间"和"推荐资源或具体方法"
- "核心能力要求"区分"必选"和"加分"两级

**不足**：
- **"JD 潜台词"的差距程度缺乏定义**：示例中"高/中/低"没有具体标准，AI 可能对同一 JD 给出不同的差距判断
- **"KPI/考核指标"的格式过于宽松**：只说"推断可能的考核方式和指标"，没有要求具体格式（如是否需要量化指标、是否需要分优先级）
- **"团队协作模式"缺少协作频率/深度的要求**：只要求"列出需要协作的角色和协作内容"，没有要求说明协作频率（日常/偶尔）和协作深度（简单沟通/深度协作）

#### 4. 可执行性（4/5）

**优势**：
- "行动建议"维度的可执行性设计优秀：要求"预计时间 + 推荐资源 + 原因"，用户可以直接照做
- "核心能力要求"区分必选/加分，帮助用户优先级排序
- "差距分析"要求"列出差距项和优先补强建议"，指导性强

**不足**：
- **时间占比的可执行性存疑**：要求 AI 给出百分比时间分配，但 AI 没有真实工作体验，给出的百分比可能误导用户。例如 AI 可能说"60% 写代码、20% 开会"，但实际可能是"40% 写代码、30% 开会、30% 改 Bug"
- **缺少"优先级排序"的统一标准**：行动建议说"按优先级排序"，但没有定义排序依据（是按"面试权重"还是按"学习曲线"还是按"投入产出比"？）

#### 5. 差异性（4/5）

**优势**：
- 知识库注入机制是核心差异化能力，将从业者经验直接注入 Prompt
- 幻觉边界规则确保差异化信息不变成编造信息
- 结构化分层报告（核心/扩展/个性化）比直接问 ChatGPT 的自由格式回答更有价值
- JD 原文优先原则确保解读有据可依

**不足**：
- **种子数据覆盖面有限**：当前仅 3 个 JSON 文件（frontend-backend、product-operations、design-data），共 6 条经验。对于同一类别的不同级别岗位（如初级前端 vs 字节跳动前端），差异化信息可能不足
- **缺少"竞品对比"差异化**：Prompt 没有要求 AI 对比"直接看 JD"和"看解读报告"的信息增量，用户可能感知不到差异化的价值
- **知识注入格式过于紧凑**：`formatExperienceForPrompt` 将经验压缩为纯文本，丢失了 JSON 中的结构化信息（如 `quality_score`、`review_status`），可能导致 AI 无法区分高质量和低质量的经验

## 二、工程质量评估

### 2.1 检查结果总览

| # | 检查项 | 评估 | 说明 |
|---|--------|------|------|
| 1 | Prompt 模板是否可直接使用（除占位符外） | **通过** | 模板结构完整，除 4 个占位符外无其他需要手动替换的内容 |
| 2 | 占位符设计是否合理 | **通过** | 4 个占位符（`{KNOWLEDGE_INJECTION}`、`{JD_TEXT}`、`{JOB_CATEGORY}`、`{USER_BACKGROUND}`）语义清晰，与代码实现一致 |
| 3 | 幻觉边界规则是否完整且可执行 | **基本通过** | 5 条规则覆盖主要风险，但缺少"时间占比编造"和"行业经验编造"的约束（详见第一部分） |
| 4 | 输出维度是否与 feature-spec.md 一致 | **通过** | 3 核心 + 4 扩展 + 1 个性化维度完全对齐 |
| 5 | 格式化层压缩率是否达标（>25%） | **待验证** | 代码逻辑正确（去除 JSON 结构标记和 meta 元数据），但需实际运行测试确认 |
| 6 | 检索模块是否能正确匹配岗位类别 | **基本通过** | 混合检索（关键词 0.6 + 语义 0.4）逻辑合理，但 Jaccard 相似度对中文的语义理解能力有限 |
| 7 | 代码是否可直接运行 | **通过** | prompt-builder.js 和 knowledge-retriever.js 代码结构清晰，依赖仅 Node.js 内置模块（fs、path），可直接运行 |

### 2.2 详细分析

#### 占位符设计（检查项 2）

4 个占位符设计合理，但有一个潜在问题：

- `{JOB_CATEGORY}` 接收的是 `category_name`（如"前端开发"），而非 `category_id`（如"frontend"）。在 `prompt-builder.js` 第 56-58 行，代码将 `category_id` 转换为 `category_name` 后注入。这个设计是合理的，因为 LLM 更容易理解自然语言类别名。

#### 幻觉边界规则完整性（检查项 3）

对照 `hallucination-boundaries.md` 中的 5 类风险：

| 风险类型 | Prompt 中是否有对应规则 | 覆盖程度 |
|----------|----------------------|---------|
| 编造来源 | 规则 1 + 规则 5 | 完全覆盖 |
| 编造数据 | 规则 2 | 完全覆盖 |
| 过度泛化 | 规则 3 | 完全覆盖 |
| 过时信息 | **无** | 未覆盖 |
| 确信度伪装 | 规则 3 | 部分覆盖 |

**缺失**：没有约束 AI 引用过时的技术栈版本或市场行情。例如 AI 可能说"目前 Vue 2 仍是主流"，但实际上 Vue 3 已成为主流。

#### 检索模块匹配能力（检查项 6）

`knowledge-retriever.js` 的检索策略分析：

**优势**：
- 混合检索（关键词匹配 0.6 + Jaccard 语义相似度 0.4）比单一检索更稳健
- 指定 category 时先过滤再排序，减少跨类别误匹配
- 中文分词支持 bigram 切分，提高中文匹配率
- 停用词表覆盖了 JD 高频虚词

**不足**：
- **Jaccard 相似度对中文语义理解能力有限**：Jaccard 基于词袋交集/并集，无法理解同义词（如"前端"和"Web 开发"是同义词但词袋无交集）
- **仅返回 Top-2 经验**：当同一类别有多条经验时（如前端有 2 条），可能遗漏有价值的经验片段
- **无相关性阈值过滤**：即使所有候选经验的得分都很低，仍会返回 Top-2，可能导致注入不相关的经验

#### 代码可运行性（检查项 7）

代码质量良好：
- `prompt-builder.js`：模板提取使用正则匹配 ` ```markdown...``` `，与 v1-jd-parser.md 的格式一致
- `knowledge-retriever.js`：纯 Node.js 实现，无外部依赖
- `test-retriever.js`：测试覆盖 4 个维度（加载、检索、压缩、构建），断言清晰

**潜在问题**：
- `prompt-builder.js` 第 104 行的正则 `/```markdown\n([\s\S]*?)```/` 要求模板中的 markdown 代码块以 ` ```markdown\n ` 开头。如果模板文件格式有微小变化（如多了空格），会导致提取失败。建议增加容错处理。

   协助产品经理完成产品业务流程设计和交互界面设计。在大多数情况下，初级产品经理以执行和辅助为主，核心设计决策由高级产品经理主导。

> 注：以上时间占比为基于从业者社区公开讨论整理的常见分配，因公司和团队而异。

### 二、核心能力要求

**必选技能：**
1. **原型设计工具（Axure/Xmind/墨刀）** — 熟练
   JD 明确要求，是日常工作核心工具。需能独立绘制中低保真原型和业务流程图。
2. **文档写作能力** — 熟练
   JD 隐含要求（需求编写、产品手册），需能编写清晰、结构化的 PRD 和产品文档。
3. **沟通协调能力** — 熟练
   JD 明确要求"跨部门沟通"和"推动各部门资源"，是日常工作的核心能力。

**加分技能：**
1. **软件开发或相关工作经验** — 了解
   JD 明确标注"优先"，有助于理解技术实现和与开发团队沟通。
2. **互联网行业经验** — 了解
   JD 加分项提及，有助于理解互联网产品的用户需求和商业模式。

### 三、行动建议

1. **熟练掌握原型设计工具** — 预计 2-4 周
   - 推荐资源：Axure 官方教程 + B 站 Axure 实战教程 + 用墨刀临摹 2-3 个 App 界面
   - 原因：JD 明确要求，面试时通常需要展示原型作品

2. **学习 PRD 编写方法** — 预计 2-3 周
   - 推荐资源：《产品经理实战》相关章节 + 参考开源 PRD 模板
   - 原因：需求文档编写是日常核心工作

3. **积累项目推进经验** — 预计 1-2 个月
   - 推荐资源：阅读《敏捷项目管理》+ 参与校内/开源项目的管理实践
   - 原因：JD 强调"跨部门沟通"和"项目推进"，这是初级产品经理的常见短板

4. **了解基础技术概念** — 预计 2 周
   - 推荐资源：《产品经理的技术课》或类似入门材料
   - 原因：有助于与开发团队沟通，JD 加分项也提到"软件开发经验优先"

### 五、KPI/考核指标

根据 JD 中的描述，可能的考核方式包括：
1. **需求交付质量** — 需求文档的完整性和准确性，需求变更率
2. **项目推进效率** — 产品功能按时上线率，延期次数

> 注：具体考核方式因公司和团队而异，以上仅为常见情况的推断。

### 六、团队协作模式

根据 JD 分析，日常需要与以下角色协作：
1. **高级产品经理** — 需求审核、方案评审、工作指导（JD 明确提及"协助产品经理"）
2. **UI 设计师** — 设计需求对接、原型评审、视觉稿验收（JD 明确提及"推动UI"）
3. **开发工程师** — 需求评审、技术可行性沟通、开发进度跟踪（JD 明确提及"推动开发"）
4. **测试工程师** — 测试用例评审、功能验收、Bug 跟踪（JD 明确提及"测试"）

### 七、工作强度信号

从 JD 中识别到的工作强度信号：
1. **"负责项目推进过程中的跨部门沟通"** — 在大多数情况下，跨部门沟通协调是初级产品经理压力较大的工作，可能需要处理多方冲突和紧急需求

> 注：工作强度因公司和团队而异，以上仅为基于 JD 用词的推断。

**发现的问题**：
1. JD 中大量使用"协助"一词，AI 需要判断"协助"的真实含义——是真正的辅助，还是"名义上协助实际上独立负责"。这个判断高度依赖经验，AI 合成数据可能不够准确
2. JD 信息量适中，但缺少行业背景（仅"加分项：互联网行业经验"），AI 难以判断具体的产品类型和业务场景
3. "编订产品手册"这一职责在知识库经验中可能被低估，实际工作中产品文档编写可能占更多时间

## 四、改进建议（V1 -> V2，按优先级排序）

### P0：必须修复（影响核心质量）

#### 1. 增加"时间占比"幻觉约束

**问题**：Prompt 要求 AI 给出时间占比百分比，但没有约束来源，AI 可能凭空编造不合理的比例。

**建议**：在幻觉边界规则中新增第 6 条：

```
## 规则 6：时间占比诚实标注

"真实工作内容"维度中的时间占比必须基于知识库中的经验数据。
如果知识库中没有相关数据，使用以下方式之一：
- "因公司和团队而异，无法给出准确比例"
- "根据从业者社区公开讨论，在大多数情况下..."

禁止凭空编造精确的时间百分比。
```

#### 2. 增加"过时信息"防护

**问题**：hallucination-boundaries.md 识别了"过时信息"风险，但 Prompt 中没有对应规则。

**建议**：在幻觉边界规则中增加：

```
## 规则 7：技术栈时效性声明

在提及具体技术栈或工具时，如果知识库数据可能存在时效性问题，
添加如下声明："技术栈要求因公司而异，以上为当前常见情况，建议以最新招聘信息为准。"
```

#### 3. JD 潜台词"差距程度"量化标准

**问题**："高/中/低"缺乏定义，AI 判断不一致。

**建议**：增加定义：
- **高**：JD 描述与实际工作内容存在本质差异（如"架构设计"实际是"按已有架构写代码"）
- **中**：JD 描述有一定夸大，但方向基本正确（如"参与设计"实际是"辅助设计"）
- **低**：JD 描述基本准确，仅有轻微包装

### P1：建议改进（提升质量）

#### 4. 行动建议增加"优先级排序依据"

**建议**：在行动建议的格式要求中增加：
```
- 每条建议需标注优先级排序依据（面试权重 / 学习曲线 / 投入产出比）
```

#### 5. KPI/考核指标增加格式约束

**建议**：增加具体格式要求：
```
- 每个考核指标需说明：指标名称 + 可能的衡量方式 + 数据来源提示
- 使用不确定性表述
```

#### 6. 检索模块增加相关性阈值

**问题**：当前检索模块即使所有候选经验得分都很低，仍会返回 Top-2。

**建议**：在 `knowledge-retriever.js` 的 `retrieve` 方法中增加最低得分阈值（如 hybrid score < 0.1 时不返回该经验），并在 Prompt 中增加处理逻辑：
```
如果知识库中没有与该 JD 高度相关的经验数据，
请在"真实工作内容"维度中说明："暂无该岗位的详细经验数据，以下分析主要基于 JD 原文。"
```

#### 7. 扩展维度增加"信息密度不足"的处理

**问题**：当 JD 信息量极少（如 jd_001 仅 6 行），扩展维度可能被迫输出低质量内容。

**建议**：增加规则：
```
如果 JD 原文信息不足以支撑某个扩展维度的分析（如 JD 仅有 3 条职责描述），
优先跳过该维度，标注"JD 信息不足，无法判断"，而非强行输出推测内容。
```

### P2：优化建议（提升体验）

#### 8. 知识注入增加质量权重

**问题**：`formatExperienceForPrompt` 丢弃了 `quality_score` 和 `review_status`，AI 无法区分经验质量。

**建议**：在格式化文本中增加质量标识：
```
### 经验 1（质量评分：4.5/5）
```
让 AI 在引用经验时可以优先参考高质量数据。

#### 9. 增加"信息增量"提示

**建议**：在报告开头增加一段引导语：
```
> 本报告基于 JD 原文和从业者社区经验，为你揭示 JD 背后的真实信息。
> 标注 [经验补充] 的内容为从业者社区公开讨论整理的额外信息，JD 中未直接提及。
```

#### 10. 模板提取增加容错处理

**问题**：`prompt-builder.js` 的正则匹配对模板格式要求严格。

**建议**：增加多种格式的容错匹配，或改为使用明确的分隔标记（如 `<!-- PROMPT_START -->` 和 `<!-- PROMPT_END -->`）。

## 五、总结

### V1 Prompt 模板整体评价

V1 Prompt 模板在结构设计上表现优秀，8 个输出维度（3 核心 + 4 扩展 + 1 个性化）与 feature-spec 完全对齐，幻觉边界规则覆盖了主要风险点，格式化示例清晰可执行。作为 V1 版本，已经达到了 metrics-framework.md 中定义的"通过标准"（总分 >= 20/25）。

**核心优势**：
- 结构化分层设计（核心/扩展/个性化）清晰合理
- 幻觉边界规则 5 条硬规则 + 质量自检清单 12 项，双重保障
- 每个维度都有详细的格式要求和示例，AI 可执行性强
- 工程实现（检索模块 + Prompt 构建器）代码质量高，可直接运行

**核心风险**：
- 时间占比缺乏幻觉约束，可能误导用户
- 种子数据覆盖面有限（6 条经验），差异化天花板受限
- Jaccard 语义相似度对中文理解能力有限，检索精度可能不足
- JD 信息量极少时，扩展维度可能输出低质量推测内容

**V1 基线总分：21/25**，达到 Phase 3 的"V1 基线质量"目标（>=15/25），且接近"优秀标准"（>=22/25）。

**V2 目标**：通过修复 P0 和 P1 级改进项，争取总分达到 >= 23/25。
