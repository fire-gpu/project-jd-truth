## 议题 1：Phase 2 知识库构建质量

### 核心论点

12 条合成数据在 Demo 阶段完全够用，数据结构设计合理且可扩展，已发现的问题均为可快速修复的工程瑕疵，不影响后续开发推进。

### 论据

**论据 1：12 条数据满足 Demo 演示需求，且已超出指标要求。**

`metrics-framework.md` Phase 2 指标明确要求"种子数据量 >= 5 个岗位"，实际交付了 6 个岗位类别（前端/后端/产品/运营/设计/数据分析），每岗位 2 条经验，共 12 条。这不是"勉强达标"，而是超额完成。Review 报告自己也承认"6 个岗位 x 2 条经验 = 12 条数据，对于 Demo 演示基本够用"（REVIEW-report.md 第 290 行）。

**论据 2：数据信息密度高，单条数据质量在 AI 生成数据中属于上乘。**

12 条经验共 48,189 字符，平均每条约 4,016 字符。每条经验包含 5 个 daily_tasks + 3-4 个 jd_vs_reality + 8 个 skills + 4 条 advice。`jd_vs_reality` 平均 200-300 字，包含具体场景描述和对比分析；`daily_tasks` 的 detail 字段平均 80-150 字，具体到工具名称（Figma、Jira、Axure）。gap_level 分布中"高差距"占 58%，完全符合产品"揭示 JD 真相"的定位（REVIEW-report.md 第 117-129 行）。

**论据 3：数据结构设计分层清晰，已为后续扩展预留接口。**

`data-schema.md` 明确列出四大设计原则：可扩展、可追溯、可贡献、可验证。`Experience` 对象的四大模块（work_content / core_skills / entry_advice / meta）完整覆盖了产品核心输出维度。meta 字段预留了 `contributor`、`review_status`、`quality_score`，直接为后续 UGC 机制做好准备。`jd_vs_reality` 字段更是直接对齐产品核心价值主张（REVIEW-report.md 第 29-34 行）。

**论据 4：ID 重复等问题已被明确识别，修复成本极低。**

Review 报告将 ID 重复列为 P0 问题，建议改为带命名空间的 ID（如 `fe-001`、`pm-001`），预估修复时间仅 2 小时（REVIEW-report.md 第 387-388 行）。tech-architecture.md 与 data-schema.md 的结构不一致问题，也只需标注"示意"或统一引用即可解决。这些都是典型的"发现即解决"级别的工程瑕疵，不是架构缺陷。

**论据 5：JSON 作为 Demo 阶段存储方案是正确选择。**

Review 报告明确指出"Demo 阶段完全可行，且是正确的选择"（REVIEW-report.md 第 47 行）。零部署成本、Git diff 可读、适合 SOLO 辅助开发场景。`tech-architecture.md` 的技术选型也确认了"SQLite / JSON 文件 -- Demo 阶段够用，无需部署"（tech-architecture.md 第 145 行）。

### 对反方可能攻击点的预判和防御

**攻击点 1："只有 12 条数据，覆盖度太低，用户输入非 6 类岗位时系统会崩溃。"**

防御：这不是 Phase 2 的问题，而是产品边界管理的问题。`feature-spec.md` 明确设计了"选择岗位类别"这一交互步骤（feature-spec.md 第 90 行），用户只能从 6 个类别中选择。Demo 的目的不是覆盖所有岗位，而是验证核心链路（JD 输入 -> 知识注入 -> AI 解读 -> 结构化报告）。如果 Demo 成功，后续扩展数据覆盖度是 V0.5 的任务，不是 Phase 2 的任务。

**攻击点 2："只有初级（0-2年）视角，缺少中级/高级经验。"**

防御：`README.md` 明确目标用户是"毕业 0-2 年的求职困难群体"（README.md 第 10 行）。产品定位就是服务初级岗位求职者，初级视角的经验数据恰好与目标用户匹配。中级/高级经验是后续版本的需求，不应在 Demo 阶段增加不必要的复杂度。

**攻击点 3："ID 重复是严重 Bug，说明工程质量不过关。"**

防御：ID 重复是一个已被自动化校验发现并明确记录的问题，修复方案清晰，预估 2 小时。在敏捷开发中，发现问题并快速修复才是工程能力的体现，而不是从未发现问题。Review 报告的自动化校验机制本身就是工程规范的一部分。

## 议题 2：当下能不能/该不该做 RAG？

### 核心论点

Demo 阶段（截止 5.10）做向量检索 RAG 投入产出比极低，关键词匹配 + 全量注入方案在当前数据规模下效果等价，且架构已预留升级接口，不存在技术债务。

### 论据

**论据 1：技术架构文档已明确论证了 Demo 阶段不做向量检索的合理性。**

`tech-architecture.md` 专设章节"为什么 Demo 阶段不做向量检索？"，给出三条理由：时间成本（向量数据库搭建 + Embedding 模型选择 + 检索调优至少 2-3 天）、数据量（种子数据只有 5-10 个岗位，向量检索优势体现不出来）、可替代性（关键词匹配 + 岗位类别映射在数据量小时效果相当）（tech-architecture.md 第 46-49 行）。

**论据 2：当前数据规模下，向量检索的收益为零。**

向量检索 RAG 的核心价值在于"从大量知识中语义相关地检索出最匹配的片段"。当前每岗位仅 2 条经验，匹配到岗位类别后全量注入仅需约 12,000 tokens，远低于豆包/DeepSeek 的 32K-128K 上下文窗口（REVIEW-report.md 第 217 行）。在只有 2 条数据的情况下做 Top-K 检索，K 只能取 1 或 2，这和全量注入没有本质区别。

**论据 3：关键词匹配 + 全量注入在 Demo 阶段有明确的工程优势。**

- **零外部依赖**：不需要 Embedding 模型、不需要向量数据库、不需要额外的 API 调用成本
- **完全确定性**：同样的输入永远得到同样的输出，便于调试和测试
- **开发速度快**：`data-schema.md` 中已给出完整的 V1 检索代码示例（data-schema.md 第 137-149 行），直接可用
- **Token 消耗可控**：Review 报告估算单次注入约 12,000 tokens，加上系统 Prompt 和用户输入，总计约 20,000-25,000 tokens，完全在预算内（REVIEW-report.md 第 220 行）

**论据 4：架构已预留升级路径，不存在"做了就回不去"的锁定风险。**

`tech-architecture.md` 设计了 `KnowledgeRetriever` 抽象类，V1 用关键词匹配，V2 可直接替换为向量检索（tech-architecture.md 第 70-79 行）。`data-schema.md` 也明确规划了"V2：向量检索（后续升级）"的检索策略（data-schema.md 第 151-166 行）。当前方案是"先跑通链路，再优化检索"，不是"不做 RAG"。

**论据 5：时间约束决定了优先级。**

项目截止日期为 2026-05-10（feature-spec.md 第 6 行），`README.md` 的执行计划中知识库构建只分配了 Day 3 一天（README.md 第 73 行）。在 1 天的预算内，完成 6 个岗位 x 2 条经验的数据构建 + Schema 定义 + 检索逻辑，已经是合理的产出。花 2-3 天做向量检索，意味着挤占 Prompt 工程（Day 4）或开发实现（Day 5-7）的时间，整体风险更大。

### 对反方可能攻击点的预判和防御

**攻击点 1："当前方案严格意义上不算 RAG，是 Knowledge-Injected Prompt Engineering，名不副实。"**

防御：命名准确性的问题不应阻碍工程推进。`feature-spec.md` 中 F3 功能描述为"检索方式：关键词匹配 + 岗位类别映射"（feature-spec.md 第 57 行），从未声称 Demo 阶段实现完整 RAG。Review 报告自己也承认"更准确的命名应该是 Knowledge-Injected Prompt Engineering"（REVIEW-report.md 第 99 行），但这并不影响功能效果。Demo 的目标是验证"知识注入能否提升解读质量"，而不是验证"检索算法的先进性"。

**攻击点 2："数据量增长后全量注入会超出上下文窗口，现在不做 RAG 就是技术债务。"**

防御：这是一个"未来可能的问题"，不是"当前必须解决的问题"。当数据量增长到需要向量检索时，`KnowledgeRetriever` 的抽象设计允许无缝替换实现。提前优化（Premature Optimization）是软件工程的经典反模式。当前阶段最重要的是验证产品价值假设，而不是构建可扩展的基础设施。

**攻击点 3："不做 RAG，跨类别检索怎么办？比如一个 JD 同时涉及前端和产品。"**

防御：`feature-spec.md` 的交互流程中，用户需要"选择岗位类别"（feature-spec.md 第 90 行），这是一个单选操作。如果未来需要支持多岗位，可以扩展为多选 + 多类别数据合并注入，仍然不需要向量检索。跨类别检索是 V0.5+ 的需求，不应在 Demo 阶段解决。

## 议题 3：数据真实性与幻觉边界

### 核心论点

合成数据在 Demo 阶段完全可接受，且当前数据质量高、与真实从业者经验高度一致；通过 Prompt 工程可以明确划定"幻觉边界"，将合成数据的负面影响降到最低；低成本获取真实数据的路径已经规划清晰，不需要在 Demo 前完成。

### 论据

**论据 1：合成数据在 Demo 阶段是行业通行做法，且当前数据质量经得起检验。**

Review 报告明确评价"数据内容高度合理且与真实从业者经验高度一致（说明 AI 生成质量很高）"（REVIEW-report.md 第 308 行）。每条 jd_vs_reality 平均 200-300 字，包含具体场景描述；daily_tasks 具体到工具名称（Figma、Jira、Axure）；entry_advice 包含具体资源推荐（书名、网站、工具名）。这不是"泛泛而谈的 AI 废话"，而是有信息密度的结构化知识。在种子数据阶段使用合成数据，是几乎所有 AI 产品的标准做法 -- 先用合成数据验证链路，再用真实数据替换。

**论据 2：指标体系对"真实性"的定义是"有明确来源"，而非"来自真实访谈"。**

`metrics-framework.md` Phase 2 指标要求"每条经验有明确来源"（metrics-framework.md 第 86 行），当前 12 条经验全部有 `source_type`（interview 或 community）和 `source_detail`，形式上完全满足。Review 报告也确认"形式上满足'有明确来源'的要求"（REVIEW-report.md 第 375-376 行）。如果反方认为"真实性"必须等于"来自真实从业者的第一手经验"，那需要修改指标定义，而不是否定当前工作。

**论据 3：通过 Prompt 工程可以有效设定"幻觉边界"，控制 AI 对合成数据的依赖程度。**

具体策略如下：

- **来源声明策略**：在系统 Prompt 中明确告知模型"以下经验数据基于公开信息整理，仅供参考，解读时请以 JD 原文为主，经验数据为辅"。这样即使合成数据有偏差，也不会主导 AI 的输出。
- **置信度标注策略**：在注入经验数据时，为每条经验添加置信度标签（如"高置信度：多个来源一致" vs "低置信度：单一来源"），让模型在引用时有所区分。
- **"不编造"硬约束**：在 Prompt 中设置硬规则"如果知识库中没有与该 JD 相关的经验，直接基于 JD 原文解读，不得编造经验数据"。这直接切断了 AI 将合成数据"幻觉放大"的路径。
- **JD 原文优先策略**：在 Prompt 中明确优先级"JD 原文 > 经验数据 > 通用知识"，确保合成数据只是补充而非替代。

这些策略都不需要修改数据本身，只需要在 Phase 3 Prompt 工程阶段实施，成本极低。

**论据 4：低成本获取真实数据的路径已经规划，且不需要在 Demo 前完成。**

Review 报告的中期建议（V0.5 阶段）和长期建议（V1.0 阶段）已经给出了清晰的数据升级路径（REVIEW-report.md 第 407-443 行）：

- **短期（Demo 阶段）**：诚实标注"经验数据由 AI 基于公开信息整理，仅供参考"
- **中期（V0.5，1-2 周）**：通过微信社群、技术论坛、脉脉等渠道收集 10-20 条真实经验
- **长期（V1.0，1-3 个月）**：启动"真实从业者访谈计划"，目标 50+ 条真实经验

`tech-architecture.md` 也设计了完整的"经验飞轮"机制（tech-architecture.md 第 123-137 行）：用户使用解读 -> 报告底部出现反馈入口 -> 用户提交真实经验 -> 后台审核 -> 入库 -> 下次同岗位解读时注入。这是一个自增长的数据飞轮，Demo 阶段只需要验证飞轮的入口设计是否合理。

**论据 5：合成数据的"系统性偏差"风险在 Demo 阶段可控。**

Review 报告指出合成数据可能存在"系统性偏差" -- "AI 倾向于生成'合理但平庸'的经验，缺少真正独特或反直觉的一手洞察"（REVIEW-report.md 第 313 行）。这个风险是真实的，但需要放在 Demo 的语境下评估：Demo 的目标是验证"知识注入能否提升解读质量"这个产品假设，而不是验证"我们的知识库比真实从业者更懂行"。只要合成数据能让 AI 的解读比"不注入知识"时更好，Demo 就成功了。真正独特的一手洞察，恰恰需要通过后续的真实数据收集来获得。

### 对反方可能攻击点的预判和防御

**攻击点 1："合成数据标注为'interview'和'community'是误导，涉嫌欺骗用户。"**

防御：这是一个严肃的指控，但与事实不符。首先，`meta.source_type` 是数据内部管理字段，用于区分数据生成方式，不是面向用户的展示字段。其次，Review 报告建议"在产品中诚实标注'经验数据由 AI 基于公开信息整理，仅供参考'"（REVIEW-report.md 第 317 行），这个建议完全合理且成本极低，应该在产品上线前实施。但"内部字段命名不够精确"和"欺骗用户"是两回事。

**攻击点 2："合成数据可能过时，比如 2026 年 React 生态可能已经变了。"**

防御：这是一个所有知识库产品都面临的共性问题，不是合成数据独有的问题。`data-schema.md` 已设计 `created_at` 字段和"经验不超过 2 年"的时效性规则（data-schema.md 第 173 行）。真实数据同样会过时，甚至可能更快（因为真实从业者分享的是过去经验，不是当前经验）。解决过时问题的正确方式是建立数据更新机制（Review 报告建议的数据版本管理和自动过期机制），而不是在 Demo 阶段追求"永不过时的数据"。

**攻击点 3："没有真实数据，怎么证明产品核心价值'真实从业者经验'？"**

防御：Demo 阶段证明的是"产品形态可行"，不是"数据来源完美"。类比：MVP 阶段用占位图片验证 UI 布局，不会有人质疑"这不是最终图片所以 UI 设计无效"。合成数据验证的是：(1) 数据结构能否支撑 AI 解读；(2) 知识注入能否提升解读质量；(3) 用户是否认为这种解读方式有价值。这三点验证通过后，再用真实数据替换合成数据，是标准的 MVP 迭代路径。

## 总结陈词

Phase 2 知识库构建工作的核心评价标准应该是：**在 Day 3 的时间预算内，是否交付了足够支撑 Demo 链路跑通的知识库？**

答案是肯定的：

1. **数据量**：6 个岗位 x 2 条经验 = 12 条，超出">= 5 个岗位"的指标要求
2. **数据质量**：信息密度高，jd_vs_reality 是亮点，gap_level 分布合理
3. **数据结构**：分层清晰，预留 UGC 和向量检索扩展接口
4. **检索方案**：关键词匹配 + 全量注入，零外部依赖，架构可升级
5. **数据来源**：合成数据在 Demo 阶段可接受，真实数据收集路径已规划

已发现的问题（ID 重复、文档结构不一致）均为 2 小时内可修复的工程瑕疵，不影响后续开发推进。

**务实的产品工程师不会在 Demo 前追求完美，而是在约束下交付可验证的最小可行产品。Phase 2 的工作正是这样做的。**
